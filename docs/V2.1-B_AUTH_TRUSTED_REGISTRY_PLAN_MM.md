# Zap v2.1-B Registry Authentication နှင့် Trusted-Registry Policy အစီအစဉ်

## 1. ရည်ရွယ်ချက်နှင့် လက်ရှိအခြေအနေ

v2.1-B ၏ ရည်ရွယ်ချက်မှာ Zap package registry များကို **ဘယ် registry ကို ယုံကြည်မည်၊ credential ကို မည်သို့ပေးမည်၊ request တစ်ခုချင်းစီတွင် authentication ကို မည်သို့အသုံးပြုမည်၊ မယုံကြည်ရသော source များကို မည်သို့တားဆီးမည်** ဆိုသည်ကို deterministic နှင့် လုံခြုံသော policy အဖြစ် သတ်မှတ်ပြီး implementation လုပ်ရန် ဖြစ်ပါသည်။ လက်ရှိ `native/src/registry.rs` တွင် local file၊ `file://` နှင့် HTTP(S) index source များကို ဖတ်နိုင်ပြီး HTTPS ကို default အဖြစ် သတ်မှတ်ထားပါသည်။ Test fixture အတွက်သာ `ZAP_ALLOW_INSECURE_HTTP=1` ဖြင့် HTTP ကို ခွင့်ပြုနိုင်ပါသည်။ Signed-index HMAC-SHA256 helper ရှိပြီးဖြစ်သော်လည်း registry authentication/trust decision နှင့် တစ်စုတစ်စည်းတည်း ချိတ်ဆက်ထားခြင်း မပြီးသေးပါ။

> အဓိကမူဝါဒ: **Authentication သည် identity ကို သက်သေပြသည်။ Trusted-registry policy သည် မည်သည့် identity နှင့် မည်သည့် endpoint ကို package operation အတွက် လက်ခံမည်ကို ဆုံးဖြတ်သည်။ Checksum သည် download လုပ်ထားသော artifact ၏ integrity ကို သက်သေပြသည်။ ထိုသုံးခုကို အစားထိုးအသုံးမပြုရပါ။**

## 2. မူဝါဒဆုံးဖြတ်ချက်များ

| မူဝါဒ | v2.1-B ဆုံးဖြတ်ချက် | အကြောင်းပြချက် |
|---|---|---|
| Transport | `https://` ကို default ခွင့်ပြုမည်။ `http://` ကို production operation တွင် reject လုပ်မည်။ `file://` နှင့် local path ကို explicit local source အဖြစ်သာ ခွင့်ပြုမည်။ | Credential နှင့် package metadata များ plaintext မဖြစ်စေရန်နှင့် လက်ရှိ secure-transport behavior မပျက်စေရန်။ |
| Registry identity | Registry ကို normalized origin အဖြစ် သတ်မှတ်မည်: scheme၊ lowercase host၊ explicit port နှင့် normalized path prefix ပါဝင်မည်။ | URL string မတူသော်လည်း endpoint တစ်ခုတည်းကို duplicate trust entry အဖြစ် မသတ်မှတ်မိရန်။ |

| Credential scope | Credential ကို registry origin နှင့် path prefix အလိုက် scope ချမည်။ အခြား host သို့ redirect ဖြစ်ပါက credential မ forward လုပ်ရ။ | Token leakage နှင့် cross-registry credential reuse ကို ကာကွယ်ရန်။ |
| Credential source | Environment variable၊ user config file နှင့် explicit CLI input ကို support လုပ်မည်။ CLI argument တွင် raw token ကို မထည့်ရန် အကြံပြုမည်။ | CI/CD နှင့် local development နှစ်မျိုးလုံးအတွက် အသုံးပြုနိုင်ပြီး shell history leakage ကို လျှော့ချရန်။ |
| Token transmission | `Authorization: Bearer <token>` ကို ပထမဆုံး authentication scheme အဖြစ် သုံးမည်။ Token ကို logs၊ diagnostics၊ lockfile နှင့် changelog တွင် မပြရ။ | Simple, interoperable နှင့် redact လုပ်ရလွယ်ကူသော contract ဖြစ်ရန်။ |
| Index signing | Signed index ကို optional hardening အဖြစ် ထည့်မည်။ Trust policy က မတောင်းဆိုပါက checksum/HTTPS များကို မဖယ်ရှားဘဲ signed-index verification ကို ထပ်တိုးမည်။ | Authentication သည် registry server identity ကို ပေးသော်လည်း cached index tampering ကို သီးခြားကာကွယ်ရန်။ |
| Redirects | Redirect များကို automatic follow မလုပ်ရ။ လိုအပ်ပါက final endpoint ကို trust policy နှင့် ထပ်စစ်ပြီး credential မပါဘဲသာ explicit redirect handling လုပ်မည်။ | SSRF နှင့် credential exfiltration အန္တရာယ်ကို လျှော့ချရန်။ |
| Offline mode | Offline operation တွင် network authentication မပြုလုပ်ရ။ Lockfile၊ trusted source metadata နှင့် verified cache များဖြင့်သာ ဆုံးဖြတ်မည်။ | Offline mode ၏ deterministic behavior ကို ထိန်းသိမ်းရန်။ |

## 3. Threat model နှင့် မကာကွယ်နိုင်သေးသော နယ်ပယ်

ကာကွယ်ရမည့် အဓိကအန္တရာယ်များမှာ မယုံကြည်ရသော registry မှ package resolution ပြုလုပ်ခြင်း၊ DNS/URL ပြောင်းလဲမှုမှတစ်ဆင့် credential ကို မသက်ဆိုင်သော host သို့ ပို့မိခြင်း၊ HTTP မှတစ်ဆင့် token ပေါက်ကြားခြင်း၊ redirect ဖြင့် trust boundary ကျော်ခြင်း၊ cached index/artifact ကို ပြောင်းလဲခြင်းနှင့် diagnostic/log ထဲတွင် secret ထွက်ပေါ်ခြင်းတို့ ဖြစ်သည်။

| Threat | Mitigation | Test requirement |
|---|---|---|
| Untrusted remote registry | Explicit trusted-origin allowlist | Unknown origin rejection fixture |
| HTTP credential exposure | HTTPS-only default; insecure HTTP test-only gate | HTTP with token must fail before request |
| Redirect to another host | No automatic redirects; final origin revalidation | Same-origin and cross-origin redirect tests |
| Token sent to wrong registry | Origin/path-scoped credential lookup | Host, port, path-prefix mismatch tests |
| Malformed or changed index | Existing JSON validation, optional signature, checksum verification | Stable malformed/signature mismatch diagnostics |
| Secret disclosure | Redaction in errors, logs, verbose output, lockfiles | Token-like pattern scan across CLI output |
| Config tampering | Strict file mode check where supported; parse with bounded size | Permissions and malformed config fixtures |
| Cache poisoning | Lockfile checksum and source/trust identity verification | Cached source mismatch and trust mismatch tests |

v2.1-B သည် malicious server မှ မှန်ကန်သော credential ရရှိပြီးနောက် ပြန်ပေးသော package ၏ business logic ကို မစစ်နိုင်ပါ။ ထိုအပိုင်းကို package signing၊ reproducible build နှင့် security audit scope တွင် နောက်ပိုင်း ထည့်သွင်းရမည်။ v2.1-B တွင် OS-level sandbox၊ hardware-backed keychain နှင့် full certificate pinning များကို မဖြစ်မနေမလုပ်သေးပါ။

## 4. အကြံပြုထားသော data model

`native/src/registry.rs` သို့မဟုတ် သီးခြား `native/src/registry_policy.rs` တွင် အောက်ပါ bounded structures များ ထည့်သွင်းရန် အကြံပြုပါသည်။ `BTreeMap` နှင့် sorted vectors ကို အသုံးပြု၍ serialization နှင့် decision order ကို deterministic ထားရမည်။

```text
RegistryOrigin {
    scheme: Https | File,
    host: Option<String>,
    port: Option<u16>,
    path_prefix: String,
}

RegistryTrust {
    origin: RegistryOrigin,
    auth_required: bool,
    allowed_auth: [Bearer],
    index_key_id: Option<String>,
}

RegistryCredential {
    origin: RegistryOrigin,
    token: String,
}

RegistryPolicy {
    trusted: sorted RegistryTrust entries,
    credentials: origin-scoped credential references,
    allow_insecure_http: false by default,
}
```

Credential တန်ဖိုးကို `Debug` output မှ ဖယ်ရှားရမည်။ `Clone` လုပ်ရသော structure များတွင် token ကို တတ်နိုင်သမျှ request lifetime အတွင်းသာ ထားပြီး error string ထဲ မထည့်ရပါ။ URL parser သည် userinfo (`https://user:pass@host`) ကို reject လုပ်ရမည်။ Hostname နှင့် path length၊ token length၊ trust-entry count တို့ကို bounded limit သတ်မှတ်ရမည်။

## 5. CLI နှင့် configuration contract

### 5.1 CLI commands

| Command | အလုပ်လုပ်ပုံ |
|---|---|
| `zap registry trust list` | Trusted registry origin များကို deterministic order ဖြင့် ပြမည်။ Credential များကို မပြပါ။ |
| `zap registry trust add <url>` | URL ကို normalize လုပ်ပြီး allowlist ထဲသို့ ထည့်မည်။ `http://` သည် explicit test/development flag မရှိလျှင် reject ဖြစ်မည်။ |
| `zap registry trust remove <url>` | Exact normalized origin ကိုသာ ဖယ်ရှားမည်။ မတွေ့ပါက stable exit code ပြမည်။ |
| `zap registry login <url>` | Token ကို interactive input သို့မဟုတ် environment reference ဖြင့် configure မည်။ Token ကို command history တွင် မရေးပါ။ |
| `zap registry logout <url>` | Origin-scoped credential ကို ဖယ်ရှားမည်။ Trust entry ကို default အားဖြင့် မဖယ်ရှားသေးပါ။ |
| `zap registry auth status <url>` | Trusted/untrusted နှင့် credential configured/missing status ကို token မဖော်ပြဘဲ ပြမည်။ |

`zap install`၊ `zap update` နှင့် `zap publish` တို့သည် registry source တစ်ခုကို အသုံးပြုမီ **normalize → trust check → credential resolve → secure transport check → request → response validate → checksum/signature verify** အစီအစဉ်အတိုင်း လုပ်ဆောင်ရမည်။ Trust check မအောင်မြင်ပါက network request မပြုလုပ်ရပါ။

### 5.2 Environment variables

| Variable | အသုံးပြုပုံ | မှတ်ချက် |
|---|---|---|
| `ZAP_REGISTRY_TOKEN` | Default registry တစ်ခုအတွက် Bearer token | Single-registry CI အတွက်သာ သင့်တော်သည်။ |
| `ZAP_REGISTRY_TOKEN_<NAME>` | Normalized registry alias အလိုက် token | Alias normalization collision မဖြစ်စေရန် config တွင် canonical origin ကို အမြဲစစ်ရမည်။ |
| `ZAP_REGISTRY_CONFIG` | Custom user/config path | Path size နှင့် permissions ကို စစ်ရမည်။ |
| `ZAP_ALLOW_INSECURE_HTTP=1` | Test fixture သို့မဟုတ် local development transport gate | Authentication ပါသော production command တွင် reject ဆက်လုပ်ရမည်။ |
| `ZAP_OFFLINE=1` | Network မသုံးဘဲ verified cache သာ အသုံးပြုခြင်း | Token ကို မဖတ်ဘဲ deterministic offline diagnostic ပြရမည်။ |

Environment variable များကို config file ထက် priority မြင့်စွာ သုံးနိုင်သော်လည်း CLI output တွင် source of credential ကိုသာ ပြပြီး token တန်ဖိုးကို မပြရပါ။

### 5.3 Project manifest နှင့် lockfile

Manifest တွင် registry alias သို့မဟုတ် canonical URL ကို သတ်မှတ်နိုင်သော်လည်း credential ကို မသိမ်းရပါ။ အကြံပြုထားသောပုံစံမှာ `registry = "company"` ကဲ့သို့ alias သတ်မှတ်ပြီး user config တွင် alias နှင့် canonical origin ကို ချိတ်ဆက်ခြင်း ဖြစ်သည်။ Lockfile တွင် resolved package အတွက် source နှင့် checksum ရှိပြီးသားဖြစ်သောကြောင့် v2.1-B တွင် `registry_origin` သို့မဟုတ် `trust_key_id` metadata ကို ထည့်လိုပါက backward-compatible optional field အဖြစ်သာ ထည့်ရမည်။ Token၊ Authorization header နှင့် secret reference ကို lockfile ထဲ မရေးရပါ။

## 6. Stable error contract

Error များကို string တစ်ခုတည်းအဖြစ် ပြန်ပေးနေသော လက်ရှိ registry path ကို မဖျက်ဘဲ internal error category/code ထည့်ပြီး CLI မှ stable message ပြသရန် အကြံပြုပါသည်။

| Code | အဓိပ္ပာယ် | ဥပမာ diagnostic |
|---|---|---|
| `REGISTRY_URL_INVALID` | URL normalize မရ | `registry URL is invalid` |
| `REGISTRY_UNTRUSTED` | Allowlist တွင် မပါ | `registry is not trusted: https://...` |
| `REGISTRY_HTTP_FORBIDDEN` | HTTP transport reject | `insecure registry transport is disabled` |
| `REGISTRY_AUTH_MISSING` | Credential မရှိ | `registry authentication is required` |
| `REGISTRY_AUTH_UNSUPPORTED` | Scheme မကိုက် | `registry authentication scheme is unsupported` |
| `REGISTRY_AUTH_FAILED` | 401/403 response | `registry authentication failed` |
| `REGISTRY_REDIRECT_FORBIDDEN` | Redirect policy ချိုးဖောက် | `registry redirect is not trusted` |
| `REGISTRY_CONFIG_INVALID` | Config format မမှန် | `registry config is invalid` |
| `REGISTRY_CONFIG_PERMISSIONS` | Secret config permissions မလုံလောက် | `registry credential file permissions are unsafe` |
| `REGISTRY_SIGNATURE_REQUIRED` | Policy အရ signature လိုအပ် | `trusted registry index signature is required` |
| `REGISTRY_SIGNATURE_INVALID` | Signature မကိုက် | `registry index signature mismatch` |

Diagnostic တွင် URL ပါပါက token query parameter၊ userinfo နှင့် secret-like query values များကို redact လုပ်ပြီး canonical origin သာ ပြသရမည်။ HTTP status code ကို authentication failure ခွဲခြားရန် internal state တွင် ထိန်းသိမ်းနိုင်သော်လည်း token သို့မဟုတ် response body ကို မပြရပါ။

## 7. အကောင်အထည်ဖော်မည့် အဆင့်များ

### Slice B1 — Policy primitives နှင့် URL normalization

ပထမဆုံး `RegistryOrigin`၊ normalization၊ equality၊ path-prefix matching နှင့် bounded parser ကို ထည့်သွင်းမည်။ Existing `require_secure_transport` ကို policy decision နှင့် ခွဲထုတ်ပြီး `file://`၊ local path၊ HTTPS၊ HTTP တို့၏ behavior ကို regression tests ဖြင့် lock လုပ်မည်။ ဒီအဆင့်တွင် network request behavior မပြောင်းသေးဘဲ decision layer ကိုသာ တည်ဆောက်မည်။

### Slice B2 — Trusted-registry allowlist

User-level config နှင့် project-level non-secret registry alias model ကို ထည့်သွင်းမည်။ `trust list/add/remove` commands များ၊ canonical output၊ duplicate detection နှင့် unknown-origin rejection ကို အကောင်အထည်ဖော်မည်။ `zap install/update/publish` တို့တွင် request မပြုမီ trust gate ချိတ်ဆက်မည်။

### Slice B3 — Credential resolution နှင့် redaction

Bearer token resolution ကို environment နှင့် bounded config file မှ support လုပ်မည်။ Credential lookup သည် exact origin သို့မဟုတ် explicitly configured path prefix နှင့်သာ match ဖြစ်ရမည်။ Request layer သည် token ကို HTTPS endpoint သို့သာ ထည့်မည်။ Error၊ verbose output၊ lockfile၊ cache metadata နှင့် test snapshots များတွင် token မပါကြောင်း regression tests ရေးမည်။

### Slice B4 — Publish/fetch/auth response handling

Index fetch၊ package download နှင့် publish request များအတွက် shared authenticated request helper ပြုလုပ်မည်။ 401/403 ကို `REGISTRY_AUTH_FAILED` အဖြစ် normalize လုပ်ပြီး 3xx ကို auto-follow မလုပ်ရ။ Redirect ရှိပါက target origin ကို trust policy နှင့် ပြန်စစ်ပြီး credential ကို မူလ request မှ မကူးစေရ။

### Slice B5 — Optional signed-index enforcement

လက်ရှိ HMAC-SHA256 verification helper ကို dead-code helper အဖြစ် မထားဘဲ registry policy မှ `signature_required` ဖြစ်သော origin များတွင်သာ အသုံးပြုမည်။ Key material ကို token နှင့် မရောစပ်ဘဲ key identifier နှင့် configuration lifecycle သီးခြားထားမည်။ v2.1-B ပထမ release တွင် shared-secret HMAC သာ သုံးမည်ဆိုပါက docs တွင် limitation ကို ရှင်းလင်းရေးသားပြီး public-key signature ကို နောက်ထပ် roadmap item အဖြစ် ခွဲထားမည်။

### Slice B6 — Documentation parity နှင့် migration

`docs/REGISTRY_AUTH_EN.md` နှင့် `docs/REGISTRY_AUTH_MM.md` အသစ်များတွင် trust model၊ CI usage၊ credential redaction၊ offline mode၊ failure diagnostics နှင့် security limitations များကို တစ်ကြောင်းချင်း parity ဖြင့် ရေးမည်။ `CHANGELOG_EN.md`၊ `CHANGELOG_MM.md` နှင့် v2.1 roadmap နှစ်ခုတွင် B1–B5 status ကို တစ်ပြေးညီ update လုပ်မည်။ Existing projects များအတွက် no-auth local/file workflow မပျက်စေရန် migration note ထည့်မည်။

## 8. Test matrix နှင့် deterministic acceptance

| Test group | မဖြစ်မနေစစ်ရမည့်အချက် |
|---|---|
| Unit tests | URL normalization၊ origin equality၊ path matching၊ config parsing၊ token redaction၊ deterministic ordering |
| Registry transport tests | HTTPS token header၊ HTTP rejection၊ missing token၊ 401/403 mapping၊ non-2xx behavior၊ no redirect credential forwarding |
| Trust policy tests | Unknown registry reject၊ trusted registry accept၊ remove then reject၊ duplicate add idempotency၊ alias mismatch |
| CLI integration tests | `trust list/add/remove`၊ `login/logout`၊ `auth status`၊ stable exit codes၊ stdout/stderr separation |
| Offline tests | Offline mode never opens network၊ verified cache accepted၊ trust/source/checksum mismatch rejected |
| Security regression tests | Token မပါသော logs/errors/lockfiles၊ userinfo rejection၊ oversized token/config rejection၊ unsafe config permissions |
| Cross-platform tests | Linux/macOS/Windows path handling၊ config directory resolution၊ file permission limitation diagnostics |
| Property/fuzz tests | URL parser၊ origin canonicalization၊ config parser၊ redaction function နှင့် malformed HTTP metadata |

Acceptance အတွက် native test suite အားလုံး pass ဖြစ်ရမည်၊ `cargo check --all-targets` နှင့် `cargo fmt --check` အောင်မြင်ရမည်၊ strict Clippy ကို CI toolchain တွင် run ရမည်၊ deterministic fixture output များ platform အလိုက် မပြောင်းရပါ။ Test token များသည် fixed non-secret placeholder များသာ ဖြစ်ရမည်။

v2.1-B ကို complete ဟု သတ်မှတ်ရန် အောက်ပါအချက်များ အားလုံး ပြည့်မီရမည်။ Remote registry တစ်ခုကို explicit trust မပြုဘဲ package operation မဖြစ်ရပါ။ Credential သည် origin/path scope အတွင်းသာ ပို့ရပြီး redirect ဖြင့် မကျော်ရပါ။ HTTP၊ 401/403၊ missing credential၊ malformed config၊ signature mismatch နှင့် offline mismatch များအတွက် stable diagnostics ရှိရမည်။ Token များသည် log၊ error၊ lockfile၊ cache metadata နှင့် changelog တစ်နေရာတွင်မျှ မပေါ်ရပါ။ Existing local/file workflows နှင့် v1/v2 lockfile compatibility မပျက်ရပါ။ English/Burmese docs parity ရှိရမည်။ နောက်ဆုံးတွင် Linux၊ Windows နှင့် macOS release gates များတွင် authenticated fetch၊ publish၊ offline install နှင့် trust failure paths များကို စစ်ဆေးပြီးမှ v2.1-B milestone ကို release-ready ဟု သတ်မှတ်ရမည်။
