# Zap Async Runtime and LSP Foundation

## Status

Zap currently provides two **foundational** P2 capabilities. The async runtime is a deterministic, single-thread executor that is ready for future async language syntax. The editor integration is a stdio JSON-RPC server that currently exposes initialization, shutdown, text synchronization, and lint diagnostics.

These foundations do not change the existing synchronous execution behavior. Full async syntax, timers, cancellation, completion, hover, formatting, and workspace indexing remain future milestones.

## Async Runtime Foundation

The native runtime exposes an internal executor with three basic operations:

| Operation | Purpose |
|---|---|
| `spawn(future)` | Add an async task to the deterministic task queue. |
| `run_until_idle()` | Poll tasks in spawn order until all tasks complete. |
| `block_on(future)` | Drive one future to completion synchronously. |

The current implementation intentionally avoids worker threads and external runtime dependencies. This gives Zap a stable semantic base before async syntax is added to the parser and evaluator.

The CLI smoke check is:

```bash
zap async-check
```

A successful result is:

```text
async runtime foundation ready
```

## LSP Foundation

Start the editor server with:

```bash
zap lsp
```

The server communicates through standard input and output using JSON-RPC messages framed with `Content-Length` headers. It currently supports the following requests and notifications:

| Message | Behavior |
|---|---|
| `initialize` | Returns Zap server information and text synchronization capability. |
| `shutdown` | Returns a successful null result. |
| `textDocument/didOpen` | Publishes diagnostics for the opened source text. |
| `textDocument/didChange` | Publishes diagnostics for the changed source text. |

The diagnostics are generated by Zap's existing lint implementation. This keeps command-line and editor diagnostics aligned instead of maintaining separate rules. When a lint message reports a source line, the server maps it to a zero-based LSP line range spanning the line's character width; diagnostics without a parsed line use the first line as a deterministic fallback.

A minimal initialize request is:

```text
Content-Length: 67\r\n
\r\n
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}
```

Editor clients should use the standard LSP transport framing and should not assume that future capabilities such as completion or hover are already available.

## Roadmap Boundary

The current executor uses a stable Rust-compatible no-op waker and remains single-threaded and deterministic. The next async work is to define language-level `async`/`await` semantics, suspension points, error propagation, timers, cancellation, and resource limits. The next LSP work is to add source ranges from the parser, precise diagnostic severities, document synchronization details, formatting, hover, completion, go-to-definition, and workspace-aware package/module indexing.
