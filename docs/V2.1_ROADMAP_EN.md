# Zap v2.1.0 Roadmap

## Release theme

> Reliable packages, a richer standard library, and structured concurrency.

Zap v2.1.0 is the next feature release after the production-hardening focus of v2.0.3. The first implementation slice strengthens package resolution while preserving Rust 1.75 compatibility, deterministic ordering, bounded I/O, and stable diagnostics.

## Status overview

| Area | Status | Acceptance direction |

## Completed v2.1-A slice

Registry index entries may now include an optional `dependencies` object:

```json
{
  "name": "web-app",
  "version": "1.0.0",
  "source": "file://web-app.pkg",
  "checksum": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "dependencies": {
    "http-core": "^1.2.0"
  }
}
```

Zap visits root requirements and nested requirements in lexical order. For each package name it selects the highest compatible registry version, keeps one version per graph, and returns the resolved set in deterministic package-name order. A cycle or incompatible repeated requirement is rejected with a deterministic diagnostic. `zap install` and `zap update` then verify existing cache entries or download and verify every selected package, subject to the configured timeout, transport, checksum, and offline policies.

The implementation is covered by native tests for transitive selection, stable result ordering, cycle detection, and version conflicts. Existing indexes without `dependencies` remain valid, so the change is backward-compatible with the v2.0.3 registry format.

## Next implementation order

### v2.1-B: Package reliability

1. Extend lockfile representation to record resolved registry packages and checksums without breaking v1 lockfiles. **Completed:** v2 emits deterministic `[resolved]` entries and v1 remains readable.
2. Add a migration/compatibility diagnostic for projects that require a newer lockfile format. **Completed:** `zap lock-migrate` is explicit, conservative, deterministic, and refuses to invent registry metadata.
3. Make `zap install` report the complete resolved graph rather than only direct manifest dependencies. **Completed:** output preserves the established count prefix and appends the complete deterministic `name@version` graph.
4. Expand offline integration fixtures with nested packages and missing-cache diagnostics. **Complete for the current slice:** fixtures now cover nested transitive resolution, missing transitive cache artifacts, cached checksum mismatches, and incomplete v2 lockfiles with stable diagnostics; additional transport and registry-service failure paths remain future work.
5. Add registry cache garbage collection with explicit dry-run output and deterministic deletion order. **Completed for the first slice:** `zap registry gc [--dry-run] [dir]` derives keep entries from a canonical lockfile, preserves referenced artifacts, removes stale and temporary files in lexical order, and refuses invalid lockfiles.
6. Define authentication and trusted-registry policy separately from the transport layer. **Transport/service failure slice completed:** insecure HTTP is rejected by default, malformed remote indexes have stable diagnostics, and non-2xx fetch/publish responses are normalized to deterministic HTTP-status errors. Authentication and trusted-registry policy design remains future work.

### v2.1-C: Standard library expansion

**First slice completed:** `file_metadata(path)` returns portable `kind`, byte `size`, and `readonly` fields using symlink-safe metadata, while `atomic_write(path, content)` uses a same-directory temporary file, sync, and rename commit with bounded content and cleanup on failure. **Second slice completed:** `from_json_typed(source, expected)` validates the decoded runtime category under the existing 8 MiB JSON limit, while `char_at`, `substring`, and `codepoints` operate on Unicode scalar values rather than UTF-8 byte offsets. **Third slice completed:** `entries(value)` returns deterministic `{key, value}` map records and `enumerate(values)` returns bounded `{index, value}` list records without mutating the input. **Fourth slice completed:** `utc_now()` returns UTC seconds and millisecond timestamps, while `duration_parts(milliseconds)` and `duration_between(end_millis, start_millis)` provide signed, checked duration decomposition with overflow diagnostics. Focused regression tests cover timestamp consistency, positive and negative durations, and invalid inputs. **Fifth slice completed:** `log_record(level, message, fields)` returns a validated structured map and `log_json(level, message, fields)` returns canonical JSON with sorted field names. Logging is pure and deterministic, with an 8 KiB message limit, 64-field limit, 256-byte field-name limit, and 64 KiB encoded-output limit. Regression tests cover canonical ordering, accepted levels, validation errors, and safety limits. The v2.1-C standard-library slice is complete; each future API must define input limits, output limits, timeout behavior, platform differences, and error codes before implementation.

### v2.1-D: Async and tooling

**First async slice completed:** the deterministic single-threaded async runtime supports `AsyncRuntime::spawn_joinable(future)`, `JoinHandle<T>::is_ready()`, and future-based output joining with explicit `SpawnError::TaskLimitReached` propagation. **Second async slice completed:** `AsyncRuntime::spawn_joinable_cancellable(future)` provides structured cancellation through `CancellationToken`, cancelled joins resolve to `JoinError::Cancelled`, and `timeout_ticks(future, ticks)` propagates deterministic poll-based `TimeoutError` results. **Third async slice completed:** `spawn_joinable_result(future)` and `spawn_joinable_result_cancellable(future)` preserve typed task failures through `TaskJoinError::Failed(E)`, with cancellation checked before inner polling and repeated joins returning `AlreadyJoined`. These slices preserve runtime task order, poll budgets, Rust 1.75 compatibility, and the no-worker-thread safety model. Regression coverage verifies successful joins, admission errors, typed failures, cancellation precedence, repeated joins, timeout failure, and timeout success; the bilingual contract is documented in `docs/ASYNC_RUNTIME_EN.md` and `docs/ASYNC_RUNTIME_MM.md`.

Remaining v2.1-D work is language-level task APIs and synchronization of formatter, LSP, and VS Code extension behavior with finalized parser and type diagnostics.

### v2.1-E: Release engineering

The first security-audit remediation slice is complete: `ZAP_UNTRUSTED=1` restricted capability mode, SSRF destination checks, disabled automatic redirects, bounded HTTP request bodies, hard process deadlines, and local registry-source restrictions are implemented and covered by regression tests. The full audit record is documented in `docs/SECURITY_AUDIT_EN.md` and `docs/SECURITY_AUDIT_MM.md`.

Next, add fuzz/property tests for lexer, parser, registry index, URL parsing, JSON conversion, and lockfile handling; add workspace-confined filesystem policy and symlink-safe canonicalization; define trusted-registry policy; and verify reproducible artifacts, installers, and Linux/Windows/macOS release gates before creating the v2.1.0 tag. Production deployments must additionally provide an OS-level sandbox, resource quotas, least-privilege credentials, and network egress controls.

## Release gates

A v2.1.0 release requires a clean working tree, Rust 1.75-compatible builds, complete native tests, strict Clippy, deterministic smoke fixtures, cross-platform target-native execution, verified checksums, and synchronized English/Burmese documentation. No feature should be marked complete solely because it works on Linux; Windows and macOS behavior must be covered by CI or an explicit documented limitation.
