## Local install/update contract

```bash
zap install [project-dir]
zap update [project-dir]
```

`zap install` is validation-only for the project manifest and lockfile. When `ZAP_REGISTRY_INDEX` is configured, it also validates exact registry entries and checksum-verified cache state; `ZAP_OFFLINE=1` permits only already-cached packages and never downloads new sources. `zap update` regenerates `zap.lock` using canonical ordering and performs the same configured registry/cache checks. For local path dependencies, it recursively validates nested manifests in lexicographic order and rejects cycles before writing or accepting the lockfile.

## `zap add` contract

```bash
zap add <name> <version> [project-dir]
```

The command updates `zap.toml` deterministically. It rejects empty or whitespace-containing names, duplicate dependency names, and invalid single-line requirements. If `zap.lock` exists, it is removed because the manifest no longer matches the lockfile. Running `zap lock` regenerates the canonical lockfile.

## Verification

The native test suite covers successful additions, lexicographic ordering, duplicate rejection, lockfile invalidation, install validation, update regeneration, idempotence, stale-lock rejection, CLI help exposure, valid local packages, missing local package manifests, nested local packages, deterministic cycle diagnostics, registry index validation, local and HTTPS transport policy, chunked/partial/truncated/slow/oversized registry response cases, cache population, checksum mismatch rejection, offline reuse, publish validation before network requests, signed-index verification and tamper rejection, deterministic cache pruning, authenticated local registry persistence, version-range selection, async parsing and evaluation, ScheduledFuture language scheduling, cooperative cancellation, poll-budget timeout, timer behavior, resource limits, poll budgets, one-poll suspension, standard-library catalog metadata and schema-2 determinism classes, bilingual policy contract, LSP capability negotiation, full-sync document versions, context-filtered completion, parser-backed hover, definitions, file-local scope-aware rename, workspace symbols, and deterministic formatting. A dependency may use `name = { path = "../local-lib" }`; the path is resolved relative to the consuming project, must contain a valid `zap.toml` with package name and version metadata, and is represented canonically in `zap.lock`. Local path dependencies are traversed depth-first in sorted dependency order. A repeated canonical path on the active traversal stack produces an error such as `dependency cycle detected: left -> right -> left`. The registry foundation now supports local and HTTPS index/artifact transport, exact and compatible version selection, signed indexes, content-addressed caching, deterministic garbage collection, SHA-256 enforcement, offline reuse, checksum-verified archive publishing, and authenticated local persistence. Metadata validation is applied to root and nested local packages before lockfile generation or update. The async language layer represents scheduled async calls as executor-backed `ScheduledFuture` values and resolves them with `await`/`task_join`; the runtime adds deterministic delay, cooperative cancellation, task limits, poll budgets, and explicit suspension. Registry transport tests cover partial/chunked/truncated/slow/oversized response cases through the bounded client reader. The M3-STDLIB-01 catalog and bilingual policy enforce explicit stability, deprecation, semver, platform, limit, timeout/error, schema-2 determinism-class, and legacy-boolean compatibility metadata. The LSP uses standard Content-Length JSON-RPC over stdio, reuses Zap lint diagnostics, preserves parser/lexer source spans for hover, definitions, and rename edits, removes closed documents from workspace state, derives completion candidates from the standard-library catalog and active document, indexes nested declarations and explicit local imports, exposes async builtin hover/signature metadata, and provides deterministic formatting. The checked-in canonical VS Code assets are validated against the catalog, and the semantic-parity harness runs in CI and release preflight. M3-DOC-01 completes the bilingual learner/reference split: the navigation hubs map each audience to a verified v2.2.3 entry point, canonical companion, and repository-relative contract. The [post-v2.2.0 remediation/provenance record](POST_V2.2.0_REMEDIATION_EN.md) records which LSP/editor/catalog corrections landed after the immutable tag and which limitations remain. Remaining boundaries are a full production reactor, multi-thread-safe task state, benchmark threshold enforcement, and external production deployment controls.
