# Zap v2.1.0 Roadmap

## Release theme

> ယုံကြည်စိတ်ချရသော package စနစ်၊ ပိုမိုပြည့်စုံသော standard library နှင့် structured concurrency။

Zap v2.1.0 သည် production hardening ကို အဓိကထားသော v2.0.3 နောက်ထွက်မည့် feature release ဖြစ်သည်။ ပထမဆုံး implementation slice သည် Rust 1.75 compatibility၊ deterministic ordering၊ bounded I/O နှင့် stable diagnostics များကို မပျက်စေဘဲ package resolution ကို ပိုမိုခိုင်မာစေသည်။

## လက်ရှိအခြေအနေ

| အပိုင်း | အခြေအနေ | ပြီးမြောက်မှုအဓိပ္ပာယ် |
|---|---|---|
| Recursive registry resolution | ပထမအဆင့်ပြီး | Direct နှင့် transitive requirements များကို deterministic အတိုင်း resolve လုပ်ပြီး package name တစ်ခုလျှင် version တစ်ခုသာရွေးခြင်း |
| Cycle detection | ပထမအဆင့်ပြီး | Active dependency cycle များကို `a -> b -> a` ကဲ့သို့ stable diagnostic ဖြင့်ပြခြင်း |
| Version conflict diagnostics | ပထမအဆင့်ပြီး | ထပ်မံတောင်းဆိုသော requirement များ မကိုက်ညီပါက cache/download မပြုမီ reject လုပ်ခြင်း |
| Transitive cache verification | ပထမအဆင့်ပြီး | ရွေးချယ်ထားသော direct/transitive package အားလုံးကို cache သို့ ထည့်ခြင်း သို့မဟုတ် checksum စစ်ခြင်း |
| Manifest/lockfile v2 format | ပထမအဆင့်ပြီး | Registry project များတွင် resolved version၊ source နှင့် SHA-256 checksum များကို pin လုပ်ပြီး legacy v1 file များကို ဆက်လက်ဖတ်နိုင်ခြင်း |
| Registry authentication policy | စီစဉ်ထား | Trusted transport၊ credential နှင့် server policy သတ်မှတ်ခြင်း |
| Cache garbage collection | ပထမအဆင့်ပြီး | `zap registry gc` သည် lockfile reference များကို ထိန်းသိမ်း၊ `--dry-run` ကို ထောက်ပံ့ပြီး candidate များကို lexical order ဖြင့် ဖယ်ရှားခြင်း |
| Transitive install reporting | ပြီးစီး | `zap install` သည် transitive package များအပါအဝင် resolved registry package အားလုံးကို stable order ဖြင့် ပြသခြင်း |

## ပြီးစီးထားသော v2.1-A အပိုင်း

Registry index entry များတွင် optional `dependencies` object ထည့်နိုင်သည်။

```json
{
  "name": "web-app",
  "version": "1.0.0",
  "source": "file://web-app.pkg",
  "checksum": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "dependencies": {
    "http-core": "^1.2.0"
  }
}
```

Zap သည် root requirements နှင့် nested requirements များကို lexical order ဖြင့် လိုက်လံစစ်ဆေးသည်။ Package name တစ်ခုချင်းစီအတွက် compatible registry version များထဲမှ အမြင့်ဆုံး version ကို ရွေးပြီး graph တစ်ခုလုံးအတွင်း version တစ်ခုတည်းကိုသာ အသုံးပြုသည်။ နောက်ဆုံး resolved set ကို package name အလိုက် deterministic order ဖြင့် ပြန်ပေးသည်။ Cycle သို့မဟုတ် ထပ်မံတောင်းဆိုမှု မကိုက်ညီခြင်းတွေ့ပါက stable diagnostic ဖြင့် reject လုပ်သည်။ ထို့နောက် `zap install` နှင့် `zap update` သည် timeout၊ transport၊ checksum နှင့် offline policy များအောက်တွင် ရွေးချယ်ထားသော package အားလုံးကို cache ထဲရှိ/မရှိ စစ်ဆေးခြင်း သို့မဟုတ် download/checksum verify ပြုလုပ်သည်။

Transitive selection၊ stable ordering၊ cycle detection နှင့် version conflict များအတွက် native tests ထည့်သွင်းထားသည်။ `dependencies` field မပါသော ရှိပြီးသား index များကို ဆက်လက်လက်ခံသောကြောင့် v2.0.3 registry format နှင့် backward-compatible ဖြစ်သည်။

## နောက်ထပ်အကောင်အထည်ဖော်မည့် အစီအစဉ်

### v2.1-B: Package reliability

1. Resolved registry packages နှင့် checksums များကို lockfile ထဲတွင် မှတ်တမ်းတင်နိုင်ရန် v1 lockfile များနှင့် မထိခိုက်သော extension ပြုလုပ်ရန်။ **ပြီးစီးပြီး:** v2 တွင် deterministic `[resolved]` entries များထည့်ပြီး v1 ကို ဆက်လက်ဖတ်နိုင်သည်။
2. Lockfile format အသစ်လိုအပ်သော project များအတွက် migration/compatibility diagnostic ထည့်ရန်။ **ပြီးစီးပြီး:** `zap lock-migrate` သည် explicit၊ conservative နှင့် deterministic ဖြစ်ပြီး registry metadata ကို မခန့်မှန်းပါ။
3. `zap install` output တွင် direct dependency များသာမက resolved graph တစ်ခုလုံးကို ပြသရန်။ **ပြီးစီးပြီး:** ယခင် count prefix ကို ထိန်းသိမ်းကာ deterministic `name@version` graph တစ်ခုလုံးကို ထပ်မံပြသသည်။
4. Nested packages၊ cache ပျောက်ဆုံးမှုနှင့် offline diagnostics များအတွက် integration fixtures ထည့်ရန်။ **လက်ရှိအပိုင်း ပြီးစီးပြီး:** nested transitive resolution၊ transitive cache ပျောက်ဆုံးမှု၊ cached checksum မကိုက်ညီမှုနှင့် မပြည့်စုံသော v2 lockfile များအတွက် stable diagnostics များကို fixture များဖြင့် စစ်ဆေးပြီးဖြစ်သည်။ Transport နှင့် registry-service failure path များကို နောက်ပိုင်းတွင် ထပ်တိုးမည်။
5. Dry-run output နှင့် deterministic deletion order ပါသော registry cache garbage collection ထည့်ရန်။ **ပထမအပိုင်း ပြီးစီးပြီး:** `zap registry gc [--dry-run] [dir]` သည် canonical lockfile မှ keep entries များကို ရယူပြီး reference ရှိသော artifact များကို ထိန်းသိမ်းကာ stale နှင့် temporary file များကို lexical order ဖြင့် ဖယ်ရှားသည်။ Lockfile မမှန်ကန်ပါက မလုပ်ဆောင်ပါ။
6. Transport layer နှင့် သီးခြားဖြစ်သော authentication နှင့် trusted-registry policy သတ်မှတ်ရန်။ **Transport/service failure အပိုင်း ပြီးစီးပြီး:** insecure HTTP ကို default အားဖြင့် reject လုပ်ခြင်း၊ malformed remote index များအတွက် stable diagnostic ပြခြင်းနှင့် non-2xx fetch/publish response များကို deterministic HTTP-status error အဖြစ် normalize လုပ်ခြင်းတို့ ထည့်သွင်းပြီးဖြစ်သည်။ Authentication နှင့် trusted-registry policy design ကို နောက်ပိုင်းတွင် ဆက်လက်လုပ်ဆောင်မည်။

### v2.1-C: Standard library တိုးချဲ့ခြင်း

**ပထမအဆင့် ပြီးစီးပါပြီ:** `file_metadata(path)` သည် symlink-safe metadata ကို အသုံးပြု၍ portable `kind`၊ byte `size` နှင့် `readonly` fields များကို ပြန်ပေးပါသည်။ `atomic_write(path, content)` သည် destination နှင့် directory တူ temporary file၊ sync နှင့် rename commit ကို အသုံးပြုပြီး content limit နှင့် failure cleanup ပါဝင်ပါသည်။ **ဒုတိယအဆင့်လည်း ပြီးစီးပါပြီ:** `from_json_typed(source, expected)` သည် လက်ရှိ 8 MiB JSON limit အောက်တွင် decoded runtime category ကို စစ်ဆေးပြီး `char_at`၊ `substring` နှင့် `codepoints` တို့သည် UTF-8 byte offset မဟုတ်ဘဲ Unicode scalar value များအပေါ် အလုပ်လုပ်ပါသည်။ ကျန်ရှိနေသေးသည်မှာ collection iteration helpers၊ UTC time/duration APIs နှင့် structured logging ဖြစ်ပါသည်။ နောက်ထပ် API တစ်ခုချင်းစီအတွက် input limits၊ output limits၊ timeout behavior၊ platform differences နှင့် error codes များကို implementation မစတင်မီ သတ်မှတ်ရမည်။

### v2.1-D: Async နှင့် tooling

Structured task spawn၊ join၊ cancellation၊ timeout propagation နှင့် error propagation များကို ပြီးစီးအောင်လုပ်ရန်။ ထို့နောက် parser နှင့် type diagnostics အသစ်များနှင့် formatter၊ LSP နှင့် VS Code extension behavior များကို synchronize လုပ်ရန်။

### v2.1-E: Release engineering

Security audit ၏ ပထမဆုံး remediation အပိုင်း ပြီးစီးပြီးဖြစ်သည်။ `ZAP_UNTRUSTED=1` restricted capability mode၊ SSRF destination checks၊ automatic redirect ပိတ်ခြင်း၊ HTTP request body limit၊ hard process deadline နှင့် local registry-source restriction များကို implementation နှင့် regression tests များဖြင့် ထည့်သွင်းထားသည်။ အသေးစိတ် audit record ကို `docs/SECURITY_AUDIT_EN.md` နှင့် `docs/SECURITY_AUDIT_MM.md` တွင် မှတ်တမ်းတင်ထားသည်။

နောက်တစ်ဆင့်တွင် lexer၊ parser၊ registry index၊ URL parsing၊ JSON conversion နှင့် lockfile handling များအတွက် fuzz/property tests ထည့်ရန်၊ workspace-confined filesystem policy နှင့် symlink-safe canonicalization ပြုလုပ်ရန်၊ trusted-registry policy သတ်မှတ်ရန်နှင့် reproducible artifact၊ installer၊ Linux/Windows/macOS release gates များကို v2.1.0 tag မတင်မီ စစ်ဆေးရန် ဖြစ်သည်။ Production deployment များတွင် OS-level sandbox၊ resource quota၊ least-privilege credential နှင့် network egress control များကို ထပ်မံလိုအပ်သည်။

## Release gates

v2.1.0 release အတွက် clean working tree၊ Rust 1.75-compatible build၊ native tests အားလုံး၊ strict Clippy၊ deterministic smoke fixtures၊ cross-platform target-native execution၊ checksum verification နှင့် English/Burmese documentation synchronization လိုအပ်သည်။ Linux တစ်ခုတည်းတွင် အလုပ်လုပ်ခြင်းကို feature complete အဖြစ် မသတ်မှတ်ဘဲ Windows နှင့် macOS behavior များကို CI သို့မဟုတ် ရှင်းလင်းသော documented limitation ဖြင့် စစ်ဆေးရမည်။
