# Zap v2.1.0 Roadmap

## Release theme

> ယုံကြည်စိတ်ချရသော package စနစ်၊ ပိုမိုပြည့်စုံသော standard library နှင့် structured concurrency။

Zap v2.1.0 သည် production hardening ကို အဓိကထားသော v2.0.3 နောက်ထွက်မည့် feature release ဖြစ်သည်။ ပထမဆုံး implementation slice သည် Rust 1.75 compatibility၊ deterministic ordering၊ bounded I/O နှင့် stable diagnostics များကို မပျက်စေဘဲ package resolution ကို ပိုမိုခိုင်မာစေသည်။

## ပြီးစီးထားသော v2.1-A အပိုင်း

Registry index entry များတွင် optional `dependencies` object ထည့်နိုင်သည်။

```json
{
  "name": "web-app",
  "version": "1.0.0",
  "source": "file://web-app.pkg",
  "checksum": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "dependencies": {
    "http-core": "^1.2.0"
  }
}
```

Zap သည် root requirements နှင့် nested requirements များကို lexical order ဖြင့် လိုက်လံစစ်ဆေးသည်။ Package name တစ်ခုချင်းစီအတွက် compatible registry version များထဲမှ အမြင့်ဆုံး version ကို ရွေးပြီး graph တစ်ခုလုံးအတွင်း version တစ်ခုတည်းကိုသာ အသုံးပြုသည်။ နောက်ဆုံး resolved set ကို package name အလိုက် deterministic order ဖြင့် ပြန်ပေးသည်။ Cycle သို့မဟုတ် ထပ်မံတောင်းဆိုမှု မကိုက်ညီခြင်းတွေ့ပါက stable diagnostic ဖြင့် reject လုပ်သည်။ ထို့နောက် `zap install` နှင့် `zap update` သည် timeout၊ transport၊ checksum နှင့် offline policy များအောက်တွင် ရွေးချယ်ထားသော package အားလုံးကို cache ထဲရှိ/မရှိ စစ်ဆေးခြင်း သို့မဟုတ် download/checksum verify ပြုလုပ်သည်။

Transitive selection၊ stable ordering၊ cycle detection နှင့် version conflict များအတွက် native tests ထည့်သွင်းထားသည်။ `dependencies` field မပါသော ရှိပြီးသား index များကို ဆက်လက်လက်ခံသောကြောင့် v2.0.3 registry format နှင့် backward-compatible ဖြစ်သည်။

## နောက်ထပ်အကောင်အထည်ဖော်မည့် အစီအစဉ်

### v2.1-B: Package reliability

1. Resolved registry packages နှင့် checksums များကို lockfile ထဲတွင် မှတ်တမ်းတင်နိုင်ရန် v1 lockfile များနှင့် မထိခိုက်သော extension ပြုလုပ်ရန်။ **ပြီးစီးပြီး:** v2 တွင် deterministic `[resolved]` entries များထည့်ပြီး v1 ကို ဆက်လက်ဖတ်နိုင်သည်။
2. Lockfile format အသစ်လိုအပ်သော project များအတွက် migration/compatibility diagnostic ထည့်ရန်။ **ပြီးစီးပြီး:** `zap lock-migrate` သည် explicit၊ conservative နှင့် deterministic ဖြစ်ပြီး registry metadata ကို မခန့်မှန်းပါ။
3. `zap install` output တွင် direct dependency များသာမက resolved graph တစ်ခုလုံးကို ပြသရန်။ **ပြီးစီးပြီး:** ယခင် count prefix ကို ထိန်းသိမ်းကာ deterministic `name@version` graph တစ်ခုလုံးကို ထပ်မံပြသသည်။
4. Nested packages၊ cache ပျောက်ဆုံးမှုနှင့် offline diagnostics များအတွက် integration fixtures ထည့်ရန်။ **လက်ရှိအပိုင်း ပြီးစီးပြီး:** nested transitive resolution၊ transitive cache ပျောက်ဆုံးမှု၊ cached checksum မကိုက်ညီမှုနှင့် မပြည့်စုံသော v2 lockfile များအတွက် stable diagnostics များကို fixture များဖြင့် စစ်ဆေးပြီးဖြစ်သည်။ Transport နှင့် registry-service failure path များကို နောက်ပိုင်းတွင် ထပ်တိုးမည်။
5. Dry-run output နှင့် deterministic deletion order ပါသော registry cache garbage collection ထည့်ရန်။ **ပထမအပိုင်း ပြီးစီးပြီး:** `zap registry gc [--dry-run] [dir]` သည် canonical lockfile မှ keep entries များကို ရယူပြီး reference ရှိသော artifact များကို ထိန်းသိမ်းကာ stale နှင့် temporary file များကို lexical order ဖြင့် ဖယ်ရှားသည်။ Lockfile မမှန်ကန်ပါက မလုပ်ဆောင်ပါ။
6. Transport layer နှင့် သီးခြားဖြစ်သော authentication နှင့် trusted-registry policy သတ်မှတ်ရန်။ **Transport/service failure အပိုင်း ပြီးစီးပြီး:** insecure HTTP ကို default အားဖြင့် reject လုပ်ခြင်း၊ malformed remote index များအတွက် stable diagnostic ပြခြင်းနှင့် non-2xx fetch/publish response များကို deterministic HTTP-status error အဖြစ် normalize လုပ်ခြင်းတို့ ထည့်သွင်းပြီးဖြစ်သည်။ **B1/B2 implementation အပိုင်း ပြီးစီးပြီး:** canonical origin၊ bounded trusted-registry policy၊ persistent `zap registry trust list|add|remove`၊ origin-scoped bearer credential၊ bounded `zap registry credential list|set|remove`၊ token validation/redaction၊ stable `ZAP-REG-AUTH-001`/`002`/`003` diagnostic နှင့် dependency resolution၊ registry fetch/cache/publish လမ်းကြောင်းများတွင် effective-policy enforcement များကို ထည့်သွင်းပြီးဖြစ်သည်။ ကျန်ရှိသည့် acceptance အလုပ်များမှာ documentation/release final review နှင့် cross-platform release integration တို့ ဖြစ်သည်။

### v2.1-C: Standard library တိုးချဲ့ခြင်း

**ပထမအဆင့် ပြီးစီးပါပြီ:** `file_metadata(path)` သည် symlink-safe metadata ကို အသုံးပြု၍ portable `kind`၊ byte `size` နှင့် `readonly` fields များကို ပြန်ပေးပါသည်။ `atomic_write(path, content)` သည် destination နှင့် directory တူ temporary file၊ sync နှင့် rename commit ကို အသုံးပြုပြီး content limit နှင့် failure cleanup ပါဝင်ပါသည်။ **ဒုတိယအဆင့်လည်း ပြီးစီးပါပြီ:** `from_json_typed(source, expected)` သည် လက်ရှိ 8 MiB JSON limit အောက်တွင် decoded runtime category ကို စစ်ဆေးပြီး `char_at`၊ `substring` နှင့် `codepoints` တို့သည် UTF-8 byte offset မဟုတ်ဘဲ Unicode scalar value များအပေါ် အလုပ်လုပ်ပါသည်။ **တတိယအဆင့်လည်း ပြီးစီးပါပြီ:** `entries(value)` သည် deterministic `{key, value}` map record များကို ပြန်ပေးပြီး `enumerate(values)` သည် bounded `{index, value}` list record များကို ပြန်ပေးပါသည်။ **စတုတ္ထအဆင့်လည်း ပြီးစီးပါပြီ:** `utc_now()` သည် UTC seconds နှင့် millisecond timestamp များကို ပြန်ပေးပြီး `duration_parts(milliseconds)` နှင့် `duration_between(end_millis, start_millis)` သည် sign ထိန်းသိမ်းထားသော checked duration decomposition နှင့် overflow diagnostic များကို ပေးပါသည်။ Timestamp consistency၊ positive/negative duration နှင့် invalid input များအတွက် focused regression tests များလည်း ထည့်သွင်းထားပါသည်။ **ပဉ္စမအဆင့်လည်း ပြီးစီးပါပြီ:** `log_record(level, message, fields)` သည် validation ပြီးသော structured map ကို ပြန်ပေးပြီး `log_json(level, message, fields)` သည် field name များကို စီထားသော canonical JSON ကို ပြန်ပေးပါသည်။ Logging သည် pure နှင့် deterministic ဖြစ်ပြီး message 8 KiB၊ field 64 ခု၊ field-name 256 bytes နှင့် encoded output 64 KiB limits များကို အသုံးပြုပါသည်။ Canonical ordering၊ လက်ခံသော level များ၊ validation error နှင့် safety limit များအတွက် regression tests များ ထည့်သွင်းထားပါသည်။ v2.1-C standard-library slice အားလုံး ပြီးစီးပါပြီ။ နောက်ထပ် API တစ်ခုချင်းစီအတွက် input limits၊ output limits၊ timeout behavior၊ platform differences နှင့် error codes များကို implementation မစတင်မီ သတ်မှတ်ရမည်။

### v2.1-D: Async နှင့် tooling

**ပထမ async အဆင့် ပြီးစီးပါပြီ:** deterministic single-threaded async runtime တွင် `AsyncRuntime::spawn_joinable(future)`၊ `JoinHandle<T>::is_ready()` နှင့် future အဖြစ် output join လုပ်နိုင်မှုတို့ကို ထည့်သွင်းပြီး `SpawnError::TaskLimitReached` ကို ပြတ်သားစွာ propagate လုပ်ပါသည်။ **ဒုတိယ async အဆင့်လည်း ပြီးစီးပါပြီ:** `AsyncRuntime::spawn_joinable_cancellable(future)` သည် `CancellationToken` ဖြင့် structured cancellation ကို ထောက်ပံ့ပြီး cancelled join များကို `JoinError::Cancelled` ဖြင့် resolve လုပ်ပါသည်။ `timeout_ticks(future, ticks)` သည် deterministic poll-based `TimeoutError` ကို propagate လုပ်ပါသည်။ **တတိယ async အဆင့်လည်း ပြီးစီးပါပြီ:** `spawn_joinable_result(future)` နှင့် `spawn_joinable_result_cancellable(future)` တို့သည် typed task failure များကို `TaskJoinError::Failed(E)` ဖြင့် ထိန်းသိမ်းပေးပြီး inner future ကို မ poll မီ cancellation ကို စစ်ဆေးကာ repeated join များကို `AlreadyJoined` ဖြင့် ပြတ်သားစွာ ပြန်ပေးပါသည်။ ဤအဆင့်များသည် runtime task order၊ poll budget၊ Rust 1.75 compatibility နှင့် worker thread မဖန်တီးသော safety model ကို ထိန်းသိမ်းထားသည်။ Successful join၊ admission error၊ typed failure၊ cancellation precedence၊ repeated join နှင့် timeout failure/success များအတွက် regression coverage ရှိပြီး bilingual contract ကို `docs/ASYNC_RUNTIME_EN.md` နှင့် `docs/ASYNC_RUNTIME_MM.md` တွင် မှတ်တမ်းတင်ထားသည်။

**စတုတ္ထ async အဆင့်လည်း ပြီးစီးပါပြီ:** evaluator နှင့် legacy expression path နှစ်ခုလုံးတွင် ရှိပြီးသား `Future` value contract ပေါ်မှ `spawn`၊ `task_join` နှင့် `task_is_ready` APIs များကို expose လုပ်ထားပါသည်။ Facade သည် arity နှင့် input type များကို စစ်ဆေးပြီး eager deterministic Future boundary ကို ထိန်းသိမ်းကာ `Future` မဟုတ်သော input ကို join လုပ်ပါက stable diagnostic ပြန်ပေးပါသည်။ Async spawn၊ readiness၊ join နှင့် invalid task input များအတွက် end-to-end regression coverage ရှိပြီး contract ကို `docs/ASYNC_RUNTIME_EN.md`၊ `docs/ASYNC_RUNTIME_MM.md`၊ `docs/ASYNC_LSP_EN.md` နှင့် `docs/ASYNC_LSP_MM.md` တွင် synchronize လုပ်ထားပါသည်။

**Tooling synchronization ပြီးစီးပါပြီ:** formatter behavior၊ LSP completion/hover/signature/formatting support နှင့် VS Code grammar validation တို့သည် finalized async task vocabulary နှင့် ### v2.1-E: Release engineering

Security audit ၏ ပထမဆုံး remediation အပိုင်း ပြီးစီးပြီးဖြစ်သည်။ `ZAP_UNTRUSTED=1` restricted capability mode၊ SSRF destination checks၊ automatic redirect ပိတ်ခြင်း၊ HTTP request body limit၊ hard process deadline နှင့် local registry-source restriction များကို implementation နှင့် regression tests များဖြင့် ထည့်သွင်းထားသည်။ အသေးစိတ် audit record ကို `docs/SECURITY_AUDIT_EN.md` နှင့် `docs/SECURITY_AUDIT_MM.md` တွင် မှတ်တမ်းတင်ထားသည်။

v2.1-E security-property အပိုင်းလည်း ပြီးစီးပါပြီ။ Deterministic adversarial corpus က URL-origin normalization idempotence၊ credential/query/fragment/traversal/separator/whitespace input များကို ငြင်းပယ်ခြင်း၊ trust နှင့် credential scope boundary၊ 64-origin allowlist limit၊ longest-prefix credential selection၊ token validation၊ secret redaction နှင့် signed-index mutation handling တို့ကို စစ်ဆေးသည်။ Signed-index corpus သည် malformed input နှင့် byte-mutated input များကို `catch_unwind` ဖြင့် run ပြီး parser panic မဖြစ်ရ၊ ပြုပြင်ထားသော index ကို လက်မခံရ ဟူသော အခြေအနေကို သတ်မှတ်ထားသည်။ ဤစစ်ဆေးမှုများကို native test suite အပြင် သီးခြား `security_property` CI step ဖြင့်လည်း run ထားသည်။

Production deployment reference အပိုင်း ပြီးစီးပါပြီ။ `deploy/zap-registry.service` တွင် protected filesystem path၊ သတ်မှတ်ထားသော writable storage၊ memory/CPU/task/file quota နှင့် loopback-only network access ပါသော least-privilege Linux supervision ကို သတ်မှတ်ထားပါသည်။ `deploy/zap-registry.nginx.conf` တွင် TLS 1.2/1.3 termination၊ HTTP-to-HTTPS redirect၊ bounded request body နှင့် proxy timeout၊ restricted method နှင့် loopback upstream များ ပါဝင်ပါသည်။ `deploy/registry.env.example` တွင် placeholder များသာ ပါပြီး `deploy/registry-deployment-policy.toml` တွင် credential/sandbox/quota/egress contract ကို မှတ်တမ်းတင်ထားပါသည်။ `scripts/validate_registry_deployment.sh` သည် secret မထုတ်ဖော်ဘဲ artifact များကို စစ်ဆေးပြီး CI တွင် သီးခြား deployment-policy gate အဖြစ် run လုပ်ပါသည်။ Repository-side controls များ ပြီးစီးသော်လည်း public operation အတွက် real certificate/DNS/ingress provisioning၊ external supervision၊ monitoring၊ OS-native sandbox equivalent နှင့် review ပြုလုပ်ထားသော egress allowlist များကို operator ဘက်မှ သီးခြား provision လုပ်ရမည်။

Workspace-confined filesystem policy နှင့် symlink-safe canonicalization ကို runtime filesystem boundary တွင် အကောင်အထည်ဖော်ပြီးဖြစ်သည်။ Relative နှင့် absolute file path များကို active project workspace အပေါ် အခြေခံ၍ resolve လုပ်ပြီး parent traversal များကို reject လုပ်သည်။ ရှိပြီးသား symlink များကို containment check မပြုမီ canonicalize လုပ်သဖြင့် workspace အပြင်သို့ ဖတ်ခြင်း သို့မဟုတ် ရေးခြင်း redirect မဖြစ်နိုင်ပါ။ Traversal attack နှင့် workspace အပြင်သို့ ညွှန်သော symlink attack များအတွက် dedicated regression coverage ထည့်သွင်းထားပြီး CI တွင် complete native suite နှင့် သီးခြား `filesystem_builtins` corpus ကို run လုပ်သည်။
